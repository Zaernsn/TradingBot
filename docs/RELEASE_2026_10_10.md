## Follow-up implementation

- Passive execution evidence persists executable quotes, bounded depth when available, expected price/fees, IOC limit, submission/acknowledgement times, and first/terminal fill observations. Reports calculate adverse signed slippage, separate EUR/base-currency fees, remaining quantity and latency. Missing observations remain missing. Existing fills and fees still use the same restart-safe REST reconciliation; no WebSocket event can book a fill.
- Settings expose optional rolling 24-hour/seven-day funding-adjusted loss limits, adverse realized slippage and consecutive failed-order limits. Defaults are zero/off. Halts persist across restarts and configuration changes, block buys, and leave protective sells available. Explicit reset requires a stopped/idle bot and no unresolved orders. It does not reset the independent drawdown halt.
- Equity checkpoints are sampled at most once per five minutes while enabled. Funding adjustment uses the existing verified deposit/withdrawal changes to `initial_equity`. Baselines are observed, not exact window-boundary prices; before enough history accumulates, evaluation uses the earliest available checkpoint. Loss limits are not guaranteed maximum losses. Historical replay uses hourly observations and cannot reproduce live order-failure/slippage halts.
- Historical tools verify the whole Kraken archive SHA256, preserve source CSVs/manifest, validate OHLCVT rows, export explicit EUR pairs at 60/15 minutes, and retain gaps rather than synthesizing candles. Dataset and research outputs stay outside Git. A separate command selects an explicit window without changing the source evidence.
- Replay-only exit policies cover fixed, ATR initial stop, trailing, maximum duration and insufficient progress. ATR sizing respects the same planned per-trade risk budget. Trailing marks only advance after a completed candle and are included in exported position state; no same-candle hindsight is used to tighten a stop. These policies are not wired into live position management.
- Offline protocol registration now supports the default automatic controller alongside hourly fast/simple momentum, normal/doubled costs and existing cash/BTC/equal-weight benchmarks. Profit factor is reported as null when no loss denominator exists. Protocol code/data identities and one-shot holdout protection remain enforced.

Follow-up schema revisions: `o61010evidence`, then `p61010guards`. Both require the normal migration-before-start deployment process.

## Offline commands

Run from `backend/` with the project's Python environment:

```text
python -m app.cli.kraken_archive ../research-data/kraken-2026Q2
python -m app.cli.kraken_history ARCHIVE.zip --sha256 PUBLISHED_SHA256 --list
python -m app.cli.kraken_history ARCHIVE.zip --sha256 PUBLISHED_SHA256 --pair BTC/EUR=EXACT_MEMBER_60.csv --output ../research-data/hourly
python -m app.cli.research_window ../research-data/hourly/manifest.json --start 2025-07-01T00:00:00+00:00 --end 2026-07-01T00:00:00+00:00 --output ../research-data/baseline-window
python -m app.cli.research register --manifest ../research-data/baseline-window/manifest.json --protocol ../docs/research-baseline-protocol.json --output ../research-runs/baseline
python -m app.cli.research run ../research-runs/baseline --candidate auto
python -m app.cli.exit_suite --manifest ../research-data/baseline-window/manifest.json --protocol ../docs/research-baseline-protocol.json --output ../research-runs/exit-suite
```

The converter requires explicit member names, not guessed Kraken aliases. Preserve failed outputs; use a new output directory for a fresh attempt. Register exit-policy variations as separate protocols before comparing them. Do not repeatedly tune against a consumed holdout.
